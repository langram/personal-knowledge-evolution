# Part III: Foundation

## Chapter 9: Content as Identity: Hash, Merkle-DAG, and Verifiable Common Knowledge

### Common knowledge needs a carrier that cannot be privatized

The first two Parts left two premises that must be put into practice. Rule three of Chapter 4 requires that all shared information, as common knowledge, be recorded and shared in a traceable, tamper-proof way. Chapter 5 requires that all the knowledge of the tools that augment human capability be held in common, and that the possibility of its being monopolized be ruled out at the root. Neither of these can rest on a paper agreement alone. This chapter is about the technical foundation that can carry them. It uses no new principle of computation; it uses what today's software engineering has already verified again and again.

### A hash is both a name and an address

The hash value obtained by running a hash algorithm over a piece of content is unique with a high enough probability to serve as that content's identifier. Change a single bit of the content and the hash value is completely different, so it can detect any tampering. Its uniqueness and uniform distribution allow fast indexing and lookup through a hash table, so it can also serve as that content's address. Write the hash values of the child objects into the content of the parent object, then hash the parent object, and so on upward, layer by layer, and you get a Merkle tree; allow several parent objects to share the same child object, and you get a Merkle-DAG: a single hash value at the root locks all the content and all the history beneath it. It is what git uses for version management, and what distributed storage and blockchain ledgers use for content addressing and tamper-proofing.

What the hash guarantees is that the content has not changed. Proving who published it still needs a digital signature: what the signature signs is precisely the hash.

So far, this technology has been used only in local scenarios of application software. My proposal is to take it as a single mechanism and run it through the whole system: design a programming language that uses hash values as the identifiers of all code and data objects in the language. A simple constant is represented by the hash value of its content; a complex object is represented by a key-value structure in which both keys and values are hash values; for a function, the hash is taken over the content of its definition. These identifiers are at the same time addresses, allowing decentralized deployment, storage and execution on a distributed network, with version management built in.

This language has three direct consequences.

First, uniqueness. Any concept, any piece of code, any datum, once its content is fixed, has a globally unique identifier, so a vast number of objects can be named without negotiation and in a distributed manner, with no collisions.

Second, dependency becomes table lookup. In traditional programming languages, cross-file and cross-software dependencies, and the complicated operations of compiling and linking, are all reduced to hash-based key-value lookups. After a low-level object is upgraded, every higher-level object that uses it can be traced automatically along the dependencies.

Third, openness becomes a requirement for running. This has to be stated precisely: the hash function itself forces no one to publish content; publishing a digest is not publishing the original. The force comes from the ecosystem's rules of admission: any code or data of a public nature that wants to enter the public dependency graph, to be referenced and run by others, must make its content obtainable and verifiable, or else nothing that references it can pass verification, and nothing that references it can run. So "closed but public" becomes, in this ecosystem, a thing that cannot run.

The third point is precisely the solution to the premise set out in Chapter 5. Existing open-source licenses only forbid closing the source in the legal sense; they cannot do it in substance: when a powerful organization violates the license, secretly develops a closed-source product, and gains an enormous advantage in competition, others cannot defeat that product by law. A language in which the hash is the name, together with this rule of admission, turns open source from a legal requirement into a running requirement: what does not publish its content cannot be referenced by others, and so cannot enter the public ecosystem. Personal private data is not included; the next chapter gives its rules.

### Everything is a tree

All code and data, as semantic objects, are tree-structured in essence; it is only that in the traditional system every level organizes this tree by its own rules: inside source code, by brackets and indentation; in data files, by their respective encoding formats; on disk, by directories; on a local network, by IP addresses; on the internet, by domain names and assorted protocols; and then each application has its own interfaces. These are all different representations of the same semantic tree, and converting between them consumes an enormous amount of the human labor in software engineering.

With Merkle-DAG, from object access inside a file to access across applications, across hosts and across the internet, the same kind of content identifier can be the name and the address, with no worry about tampering, and with packing and splitting done automatically according to the scenario in which the object is used. This idea has so far been applied only in local scenarios; what I intend to do is use it to reconstruct the whole system in a unified way.

What unification brings is not sameness. Different implementations of the same function each have a unique identifier, hang on the same tree as replaceable options, and can be evaluated against the same benchmarks, with the better implementation directly replacing the worse. This holds for software, and every product in economic life, from a single screw to a chip design, can be organized the same way. Just as in the DNA system of living things, the unification of rules and architecture does not hinder diversity; on the contrary, it unleashes diversity.

### Names are for people, identity is for machines

The computer ecosystem is full of naming diversity born of differing human preference: different instruction sets, different language syntaxes, different data formats, different keyboard shortcuts. For a long time, the developers at every link in the ecosystem were humans, and human diversity in naming and presentation has soaked into the entire software and hardware ecosystem.

The AI era has changed this. The construction of software is being carried out by AI-capable computers iterating on themselves; humans retreat to the outside of the ecosystem and interact with it through input and output. That being so, the internal operation has no need to keep using human natural language as the rules of naming and syntax. It is like a fully automated production line: there is no need for the robotic arm to imitate human limbs. Natural language and graphical interfaces will henceforth serve only as the interface for interacting with humans; inside the system, the hash is the identity.

Doing this also solves an old problem. Human naming tends to give the same name to different things: something called addition might be unlimited-precision, might wrap on overflow, might be floating-point addition with a specific rounding rule. With content as identity, any difference in implementation is reliably reflected as a difference of identity.

### Compatibility first, then replacement

The new foundation cannot require the world to abandon the old ecosystem first. My approach is compatibility first, then replacement: with AI presiding, describe the old system's code interfaces, data formats and calling conventions as a Merkle-DAG structure; first wrap the old object in a wrapping layer, so that seen from outside it is no different from a new object and can be put to use immediately; at the same time, on the inside, progressively analyze dependencies, construct replacement implementations, verify them, and then take over piece by piece. I call this AI-driven migration mechanism the software seed: a seed is planted on an application, a device, the whole of a person's digital resources, or even an organization; it develops on its own and completes the wrapping and the replacement. As long as every replacement is functionally equivalent, the whole process is smooth and imperceptible to the user.

Working together with it are the cold path and the hot path. A person learning to drive has to think through every action at first; after repeated training, the thinking process is compressed into muscle memory. Software is the same: when a new task appears for the first time, a large model thinks it through and writes it on the spot, and this is the cold path; once verified to work well, it is solidified into a reusable program that is called directly the next time, and this is the hot path. All users share their hot paths with one another: as soon as one person has implemented something, everyone can use it directly; when someone produces a more efficient implementation, after evaluation it becomes the new version.

### How to know it is actually better

Someone will say that ordinary software can achieve these capabilities too. That sentence only shows that they do not depend on a new principle of computation; it does not answer the other question: can different participants across the globe continuously combine their respective results at a lower cost of coordination? The hardware of computer networks had long been mature, but it was not until protocols like TCP/IP and HTTP appeared that the information revolution truly began. Sometimes no brand-new technology is needed; a new way of building is enough to produce revolutionary change.

The variables truly worth measuring are these: how many independent participants can reuse one act of creation? How much new wiring work does adding one participant require? How fast can one improvement propagate while preserving quality and control over data? The test that best decides the prospects is a small closed ecosystem loop: several independently developed applications sharing, under a common contract, one intermediate result and one replaceable function; a new participant completing a composition without modifying the original applications; an implementation, once improved, adopted by other participants after independent verification. Against a mature ordinary solution, compare wiring hours, change-propagation cost and reuse rate. If, when the fourth application and the second implementation are added, the added work keeps dropping significantly, then direct evidence for this way of building begins to accumulate. This test is what my own project is doing, and it has already produced negative results that must be recorded truthfully.

### Questions and Answers

**Q: Content addressing can only confirm byte identity; it does not decide whether two programs are semantically the same, nor does it prove that the code is not malicious. Does the word "unification" hide unsolved problems inside it?**

A: The hash guarantees three things: the same content gets the same identity, different content gets different identities, and given the content you can verify whether it has been replaced. Whether semantics are equivalent, which version should be chosen, whether the source is trustworthy: these are another layer of work built on top of identity. Equivalence is decided by benchmarks and verification evidence; the choice is decided by contract, load and permissions; trustworthiness is answered by the traceable contribution history recorded in the same structure. Each of these layers can be done, and each can only be done once the identity layer is clean. Take the problem of names and addresses out of human hands first, and only then do the remaining problems become, for the first time, something you can get your hands on.
